## 给 AI Agent 阅读的规范说明

下面的规范用于指导 AI agent（或协作开发者）在每次接到新需求时如何在仓库 `docs/` 目录下创建设计文档与开发总结，保证文档命名、内容、序号规则一致且可被自动化处理。

`docs/` 目录下仅包含文档，同时设计文档和总结文档只能出现在 `docs/` 目录下，代码将按照项目分别位于 `docs/` 上一级目录中。

请严格遵守下列规则：

### 1. 总体规则（必须遵守）
- 每次有新需求时，必须在仓库的 `docs/` 目录下创建对应的“设计文档”。
- 设计文档的文件名必须严格按“序号+需求名称”的格式命名（例如：`1用户登录设计.md`、`2导出功能设计.md`）。序号为整数，序号应当是 `docs/` 目录下已有文件最大序号加 1。
- 设计文档“必须且仅”包含下列三个部分（且标题必须完整）：
  1. 需求背景
  2. 现有的代码情况（包括与需求相关的代码功能实现和可用接口）
  3. 需求实现预期结果及验收标准
- 设计文档不得包含其他无关章节（例如实现细节、测试记录等应写在开发总结或代码注释中）。

### 2. 序号规则（如何确定下一个序号）
- 在创建新设计文档前，扫描 `docs/` 目录内的文件名，提取以数字开头的文件（文件名前缀连续的阿拉伯数字）。
- 解析出这些数字后，使用最大值 + 1 作为本次设计文档的序号。
- 序号可以不做前导零补齐（例如 `1`、`2`、`10` 都是允许的），但在命名时务必把序号放在文件名前端以便排序与自动识别。

### 3. 设计文档内容格式（模板）
文件应为 Markdown 格式，且仅包含下面三个一级标题（或二级标题）及其内容：

示例模板：
```
## 需求背景

（在此处简要说明为什么需要这个需求、业务背景、触发场景、关联的业务目标等）

## 现有的代码情况（包括与需求相关的代码功能实现和可用接口）

（在此处说明当前仓库中与该需求相关的模块/文件/函数/接口，指出可重用的接口、已实现的功能、重要调用流程，以及可能需要修改的点。若有可用的接口，请注明接口路径、输入输出数据结构和调用示例。）

## 需求实现预期结果及验收标准

（在此处明确实现后的预期效果、行为、性能或边界条件，以及用于验收的具体场景和断言或测试要点。例如：接口返回字段、HTTP 状态码、数据库变化、日志输出或端到端场景的通过条件。）
```
> 注意：设计文档必须清晰、简洁且可被开发者与测试者依据执行；所有验收标准应可验证。

### 4. 开发总结文档（可选，但在某些情况下必须存在）
- 开发完成后可以编写“开发总结”，文件命名格式必须为：`序号-需求名称-开发总结.md`（例如：`1-用户登录-开发总结.md`）。其中的 `序号` 必须与对应的设计文档序号完全相同。
- 若在开发过程中发现实现与设计文档描述不一致，则“必须”编写开发总结文档（即在以下情形之一必须写：需求变更、实现受限无法完全实现、接口或数据模型调整等）。
- 开发总结文档必须包含：
  1. 本次实现与原设计文档逐项对照说明（明确哪些实现了，哪些未实现以及原因）。
  2. 如果编写了测试代码或示例使用方法，必须说明使用方法与运行步骤，并且这些使用方法**必须经过测试通过**；如果没有通过测试，不允许在总结中写测试使用方法。
  3. 任何已知的限制、后续待办或回归风险。

示例模板（开发总结）：
```
## 已实现项
- 列出与设计文档中预期一致并已实现的功能点。

## 未实现项及原因
- 列出未实现或部分实现的功能点，并说明原因（例如：依赖外部服务不可用、时间不足需二期实现、设计需要调整等）。

## 测试与使用方法
- 如果包含了测试代码或使用示例，说明如何运行测试（命令、环境、必要的前置条件），并且仅在测试通过后写明示例输出或断言。若测试未通过，则不要在此处写测试步骤。

## 风险与后续建议
- 简要列出已知风险与推荐的后续工作。
```
### 5. 额外约束与注意事项
- 任何自动化脚本或 agent 在创建文件时，应保证写入的是 UTF-8 编码的 Markdown 文档。
- 请避免在设计文档内直接包含大量实现代码块（实现细节应放在代码仓库中对应的实现文件或 PR 描述里）。
- 如果需要引用仓库中特定文件或接口，请写明相对路径或文件名，并尽量引用具体函数名与行号范围（如果适用）。


如果你是自动化 agent：在创建新设计文档之前，请先读取 `docs/` 目录文件名以计算下一个序号；创建后请把文件路径（相对仓库根目录）返回给调用者，以便人工或自动后续审阅。
